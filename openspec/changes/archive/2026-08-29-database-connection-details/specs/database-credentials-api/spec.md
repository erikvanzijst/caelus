## Purpose

A deployment's database credentials are platform-held: generated by the reconciler,
encrypted at rest, and delivered into the pod as environment variables rather than as
tenant-writable vars. That makes them invisible to the person who owns the database. This
capability exposes them through a deployment-scoped read endpoint, together with the
database's quota state and usage, so an owner can see the credential they own, understand
why writes are failing, and see how close they are to their allowance — and so that a
forwarding client, when one exists, has the address it must tunnel to.

It is the platform's read model for the database, not a connection recipe: the address it
returns is in-cluster, and nothing that reads this endpoint today can reach it.

## ADDED Requirements

### Requirement: A deployment-scoped endpoint returns the database connection details
The API MUST provide a read endpoint under the deployment resource returning that deployment's database host, port, database name, role name, and password, following the platform's nested-route convention for deployment sub-resources.

Host and port MUST be the connection pooler's, never the database server's. The pooler is the only route to a tenant database and that property is enforced by network policy; publishing the server's address would advertise an endpoint that is deliberately unreachable.

#### Scenario: Owner retrieves connection details
- **WHEN** the owner requests the database details of a deployment whose database is provisioned
- **THEN** the response contains the pooler host and port, the database name, the role name, and the password

#### Scenario: The server's address is never published
- **WHEN** the response is inspected
- **THEN** the host and port it names are the pooler's

### Requirement: The response carries components, not a composed URL
The response MUST return the connection details as individual components and MUST NOT include a ready-composed `postgresql://` connection URL.

The pooler address is reachable only from inside the cluster, so a URL built around it connects from nowhere a person can type. The one URL that will ever connect is the one a forwarding client composes around its own local address, and that client must compose it itself because it is replacing the host and port. A server-composed URL would therefore be consumed by nobody while appearing in every surface that reads this endpoint.

Correct percent-encoding remains a requirement of whichever component assembles a URL, and belongs with that component.

#### Scenario: No composed URL is returned
- **WHEN** the owner reads the connection details
- **THEN** no field of the response contains a composed connection URL

### Requirement: The response reports quota state and usage
The response MUST report the database's current quota state, the size last measured, the allowance that size is measured against, and when the measurement was taken.

Usage is measured on a periodic sweep, not at request time, so the response MUST make the measurement's age visible rather than presenting a stale figure as current. A deployment whose database has never been measured MUST be distinguishable from one measured at zero.

Reporting the state is what turns two otherwise baffling failures — writes that fail on a read-only database, and logins refused on a suspended one — into something the owner can diagnose without contacting support.

#### Scenario: Read-only state is visible
- **WHEN** a deployment's database has been switched to read-only for exceeding its allowance
- **THEN** the response reports that state

#### Scenario: Suspension is visible
- **WHEN** a deployment's database has been suspended
- **THEN** the response reports that state

#### Scenario: Measurement age is visible
- **WHEN** the response reports a size
- **THEN** it also reports when that size was measured

#### Scenario: Never-measured is distinct from zero
- **WHEN** a database has been provisioned but never measured
- **THEN** the response distinguishes that from a database measured at zero bytes

### Requirement: Absence semantics mirror the platform's other credential endpoint
The endpoint MUST distinguish "this deployment has no database" from a transient error, returning a stable not-found response the UI can key on to hide the panel.

The other absence is the deployment's own and is not specific to this capability: the endpoint MUST follow the platform's existing rule for a readable deployment, under which a deployment that does not exist, one not owned by the account named in the path, and one that has been deleted all answer identically with the standard not-found, disclosing nothing about a database.

A database is provisioned during reconcile, before the deployment reaches its ready state, and provisioning failure fails the reconcile. A deployment therefore has its database whenever it is settled, and the interval in which the record does not yet exist is exactly an interval in which the deployment is not settled. The endpoint MUST NOT invent a separate "provisioning" answer for that interval: a transitional deployment is already described by its own status, and clients MUST take it from there rather than from this endpoint.

#### Scenario: Product without relational storage
- **WHEN** the owner requests details for a deployment whose product does not offer relational storage
- **THEN** the response indicates no database is available for this deployment, in a form the UI can use to hide the panel

#### Scenario: Settled deployment with relational storage has details
- **WHEN** the owner requests details for a settled deployment whose product offers relational storage
- **THEN** the response contains the connection details, because provisioning precedes the ready state

#### Scenario: Deleted deployment
- **WHEN** the owner requests details for a deleted deployment
- **THEN** the response is the platform's standard not-found, disclosing nothing about the database

#### Scenario: Deployment requested under the wrong owner
- **WHEN** an administrator requests a deployment that exists but is not owned by the account named in the path
- **THEN** the response is the platform's standard not-found

### Requirement: The password is readable by the owner alone
Reading the connection details MUST follow the platform's deployment authorization rules: the owner may read them, and a caller who is neither the owner nor an administrator MUST be refused with the platform's standard authorization error.

The **password** MUST be returned only to the owner. An administrator MUST receive the connection details without it, and the response MUST make clear that it was withheld rather than absent.

An administrator holding a tenant's database password can read that tenant's data. Administrative access exists to operate the platform, not to read what tenants store in it, and the platform already treats sensitive values this way: a var marked sensitive is write-only for everyone, administrators included.

#### Scenario: Non-owner is refused
- **WHEN** a user who is neither the owner nor an administrator requests another account's database details
- **THEN** the request is refused with the platform's standard authorization error

#### Scenario: Administrator reads details without the password
- **WHEN** an administrator requests another account's database details
- **THEN** the response contains the host, port, database name, role name, quota state and usage, and does not contain the password
- **AND** the response indicates that the password was withheld

#### Scenario: No field carries the password to an administrator
- **WHEN** an administrator reads the details
- **THEN** no returned field contains the password, in any form

### Requirement: Reading has no side effects
Reading the connection details MUST NOT rotate the password, re-provision the database, alter quota state, or modify the stored record in any way. It is a read of what already exists.

#### Scenario: Repeated reads return the same credentials
- **WHEN** the owner reads the details twice with no reconcile in between
- **THEN** both responses carry the same password

#### Scenario: Reading does not disturb quota state
- **WHEN** the details are read for a database in a degraded quota state
- **THEN** that state is unchanged by the read

### Requirement: The password is never written to a log
The password MUST NOT appear in application logs, request or response logs, error messages, or exception traces, on any path including failures.

The platform already routes this credential around its logging deliberately: merged Helm values are logged in full, which is why the database password reaches the pod through a Secret and the chart carries only references. An endpoint that logged it would defeat that.

#### Scenario: Successful read logs no secret
- **WHEN** the endpoint returns connection details
- **THEN** no log line produced by the request contains the password

#### Scenario: Failure logs no secret
- **WHEN** the request fails after the password has been decrypted
- **THEN** no log line or error response contains it

### Requirement: Operator CLI parity
The `caelus` operator CLI MUST offer the same read over the same service layer, subject to the same rules — including withholding the password from an operator who is not the deployment's owner.

#### Scenario: Operator reads details
- **WHEN** an operator reads a deployment's database details through the CLI
- **THEN** the same fields are reported as the API would report, with the password withheld under the same rule
