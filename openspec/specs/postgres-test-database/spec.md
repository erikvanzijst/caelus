# postgres-test-database Specification

## Purpose
Defines how the API test suite obtains and isolates its database, so that
tests exercise the same constraints, locking, and migration chain that run in
production instead of a permissive stand-in.

## Requirements

### Requirement: The test suite runs against a real PostgreSQL database
The API test suite SHALL execute every database-backed test against a real
PostgreSQL database, addressed by the `CAELUS_TEST_DATABASE_URL` environment
variable. There SHALL be no alternative backend and no in-memory mode.

#### Scenario: Test suite starts with a reachable PostgreSQL
- **WHEN** `pytest` starts and `CAELUS_TEST_DATABASE_URL` names a reachable
  PostgreSQL server
- **THEN** the suite SHALL run all database-backed tests against that server

#### Scenario: Developer runs the suite inside the devcontainer
- **WHEN** a developer runs the suite in the devcontainer or CI, where the
  compose stack already provides PostgreSQL
- **THEN** `CAELUS_TEST_DATABASE_URL` SHALL already be set by the environment
- **AND** no additional service, credential, or manual setup step SHALL be
  required

### Requirement: The suite fails fast when no PostgreSQL is available
When the test database cannot be resolved or reached, the suite SHALL abort
with a message naming the variable and the expected server. It SHALL NOT skip
the affected tests, and it SHALL NOT report a passing run.

#### Scenario: The environment variable is unset
- **WHEN** `pytest` starts and `CAELUS_TEST_DATABASE_URL` is unset
- **THEN** the run SHALL fail with an error explaining that a PostgreSQL test
  database is required and how to provide one

#### Scenario: The server is unreachable or the user lacks privileges
- **WHEN** the configured server cannot be connected to, or the connecting user
  may not create a database
- **THEN** the run SHALL fail with an error identifying which of the two
  conditions occurred

### Requirement: The suite owns its test database and migrates it with the real chain
The suite SHALL create its own test database if it does not exist, and SHALL
bring its schema to head by applying the project's Alembic migration chain from
scratch — not by generating tables from model metadata. Creation SHALL be
idempotent across runs.

#### Scenario: First run against an empty server
- **WHEN** the suite starts and the test database does not exist
- **THEN** the suite SHALL create it and apply the full migration chain before
  the first test runs

#### Scenario: Subsequent run against an existing test database
- **WHEN** the suite starts and the test database already exists
- **THEN** the suite SHALL reuse it and bring it to head without error

#### Scenario: The migration chain drifts from the models
- **WHEN** the schema produced by the migration chain differs from what the
  models declare
- **THEN** the affected tests SHALL fail
- **AND** the drift SHALL NOT be masked by building the test schema from model
  metadata

### Requirement: Each test starts from an empty database
Every test SHALL begin with no rows in any application table and with identity
counters reset, regardless of what preceding tests wrote or whether they
failed. Migration bookkeeping SHALL survive between tests.

#### Scenario: A test writes rows and the next test runs
- **WHEN** a test commits rows and a subsequent test begins
- **THEN** the subsequent test SHALL observe no rows in any application table

#### Scenario: A test fails partway through
- **WHEN** a test raises after committing rows
- **THEN** the following test SHALL still observe an empty database

#### Scenario: A test depends on small generated identifiers
- **WHEN** a test creates rows whose identifiers are generated by the database
- **THEN** those identifiers SHALL start from the beginning of their sequence,
  independent of how many rows earlier tests created

#### Scenario: Reset runs against a database holding auxiliary schemas
- **WHEN** other tests have created additional schemas in the test database for
  their own migration runs
- **THEN** the per-test reset SHALL affect only the application's own schema

#### Scenario: Rows exist whose deletion order violates foreign keys
- **WHEN** the tables to be emptied reference one another, including in cycles
- **THEN** the reset SHALL succeed without requiring a deletion order

### Requirement: Tests commit for real so deferred constraints fire
Test isolation SHALL NOT convert application commits into anything weaker. A
transaction committed by application code under test SHALL reach transaction
end, so that constraints deferred to COMMIT are evaluated exactly as in
production.

#### Scenario: A deployment names a release that is never created
- **WHEN** a test commits a deployment whose deferred foreign key points at a
  release row that does not exist
- **THEN** the commit SHALL be rejected by the database

#### Scenario: A deployment and its release are created in production order
- **WHEN** a test inserts a deployment naming a not-yet-existing release, then
  inserts that release, then commits
- **THEN** the commit SHALL succeed

### Requirement: Tests never operate on the development database
No test SHALL read from or write to the development database. The suite SHALL
detect and reject a run in which any database connection would resolve to it.

#### Scenario: A component resolves to the development database URL
- **WHEN** any engine created during a test run would connect to the
  development database rather than the test database
- **THEN** the run SHALL fail with an error naming the offending URL

### Requirement: Test execution is serial
The test suite's database isolation assumes a single test executing at a time
against one shared test database. Parallel execution SHALL NOT be supported
until per-worker databases are introduced.

#### Scenario: The suite is invoked with parallel workers
- **WHEN** the suite is run with more than one worker process against the same
  test database
- **THEN** isolation SHALL NOT be guaranteed, and the configuration is
  unsupported
